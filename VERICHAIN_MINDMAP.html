Architecture Mindmap — Multi-Modal Document Fraud Detection for Loan Underwriting

VeriChain Real-time document tampering & forgery detection
Frontend — React + Vite + TypeScript
  • Router (app/router.tsx) React Router 6
  • Pages
  • └ NewVerification upload+queue — FileDropzone, doc-type select, multi-file queue → submit batch
  • └ Processing — polls GET /verify/batch/{job_id} every 600ms, progress bar
  • └ Results — hero verdict gauge, cross-doc signals, document cards, underwriter Approve/Review/Reject buttons with "Recommended" badge
  • └ DocumentDetail — side-by-side viewer + signal cards, severity filter, BeforeAfterPanel for PDF revision recovery
  • └ History — persisted verification log, soft-delete
  • └ Settings
  • API Client (api/realClient.ts → adapter.ts)
  • └ Submits batch via POST /verify/batch
  • └ Polls GET /verify/batch/{job_id} for job status
  • └ Reads GET /verifications for history
  • └ Records POST …/decision for underwriter verdict
  • Adapter translates frozen backend contract → rich UI model
  • └ Risk score → Trust score (band-clamped)
  • └ Reasons → Signals with family/severity tags
  • └ Decision → Verdict (genuine | review | high_risk)
  • Components: FileDropzone, DocumentCard, DocumentViewer, ScoreGauge, VerdictPill, SignalCard, BeforeAfterPanel, FieldsTable, SeverityBadge
Backend — FastAPI + SQLite
  • main.py: App entry, CORS middleware, route mounting, DB init
  • Routes
  • └ POST /verify frozen contract — single-document verification (synchronous). Returns risk_score, route_taken, decision, reasons, blockchain_tx, field_verification
  • └ POST /verify/batch — submits n documents, returns job_id, background thread processes concurrently
  • └ GET /verify/batch/{job_id} — poll until done (cache-control: no-store)
  • └ POST /verify/batch/{job_id}/decision — underwriter's Approve/Review/Reject recorded to audit log
  • └ GET /verifications — persistent history list (survives restart)
  • └ DELETE /verifications/{job_id} — soft delete (audit log preserved)
  • process_document(): orchestrates P1 forensics → P2 verification → fusion → result
  • _decide(): auth score ≥80 → route_1/auto_approve, 60-79 → route_2/human_review, <60 → route_3/auto_reject
  • jobs.py: In-memory async job store (dict + lock)
  • store.py: SQLite persistence for verifications + blockchain_log migration, soft-delete
  • Cross-document batch: ThreadPoolExecutor runs concurrent per-document pipes → discrepancy.py → overall verdict (weakest-link + escalation)
Pipeline 1 — Authenticity & Forensics
  • Classifier (classifier.py) routing
  • └ PDF header inspection (pikepdf + PyMuPDF)
  • └ Routes to: signed_pdf, born_digital_pdf, scanned_image
  • └ Vector text ratio estimation (5-page sampling)
  • Tier 0 — Provenance strongest signal
  • └ PKCS#7 offline signature verification (signature.py) — cryptographic integrity, trust chain, post-sign modification detection
  • └ QR-code payload decoding + local registry lookup (qr.py, mock_registry.py)
  • └ SHA-256 hash → known-fake / known-genuine registry
  • Tier 1 — Structure & Typography high precision
  • └ PDF metadata diffs (Creator/Producer, CreationDate vs ModDate, XMP history)
  • └ Incremental-update revision recovery KILLER SIGNAL — reconstructs prior PDF revision, diffs original → edited values
  • └ Font family mismatch detection (per-span font vs document dominant)
  • └ Visual typography outliers (stroke density, baseline misalignment) via OCR word boxes
  • └ EXIF metadata for photos (suspicious software tags)
  • Tier 2 — Pixel Forensics advisory only
  • └ ELA (Error-Level Analysis) blockmap
  • └ DCT anomaly detection
  • └ Noise-residual analysis
  • └ Copy-move detection (forged stamps/signatures)
  • └ Multi-signal fusion: ≥2 signals overlap → high; single → low
  • └ Watermark suppression (portal/disclaimer overlays filtered)
  • IMPORTANT: Tier 2 is ADVISORY on government e-records — repeated text/table-grids/seals false-positive CSA/DCT/ELA heavily. Never drives verdict alone.
  • Tier 3 — Domain & Integrity (tamper_map/spectral.py)
  • Schema (schema.py): ClassificationResult, TierResult, SignatureResult, PixelForensicsResult, RevisionChange, SuspectRegion…
Pipeline 2 — Content Extraction & Verification
  • extract.py — dual-pass VLM extraction
    • Pass 1: vision call → full OCR + regional-script → English translation + classification (preserves entire document)
    • Pass 2: text call → derive schema-declared fields from English full_text (cheaper, judging the same content)
  • verify.py — SEPARATE LLM session, fresh context, judges on data alone
    • Compares extracted field set vs DB-of-record semantically, not string-equal
    • Handles transliteration variance, co-owners, name-order, father-name suffixes, S/o variants
    • Outputs: match_status (match | partial_match | mismatch), per-field results, discrepancies
  • validators.py — deterministic (NOT LLM) high-confidence checks
    • PAN structure (AAAAA9999A regex) + 4th-char holder type (P/C/H/F/A/T…) + 5th-char surname-initial cross-check
    • Aadhaar: full Verhoeff D5 dihedral checksum
    • GSTIN: mod-36 checksum, state-code validity, embedded-PAN match vs applicant
    • Payslip arithmetic: gross - deductions = net (absolute+relative tolerance)
    • Failures from DEFINITIVE checks override match_status→"mismatch"
  • db.py — mocked authoritative record
    • fetch_record(db_collection, key_fields, extracted_fields)
    • Land-record tolerant lookup: parcel_id (exact) → survey_number bases (fuzzy) + locality/owner overlap
    • ITR records: composite key (PAN|assessment_year)
    • Returns: {found, source, record, as_of}
  • discrepancy.py — cross-document fraud detection
    • LLM identifies attributes across documents (PAN, incomes, employer, address…)
    • Deterministic cross-checks: PAN agreement, GSTIN→PAN embedding match
    • Output: per-attribute severity + detail + document list
  • schemas.py: 30+ document schemas (ITR, payslip, land_record, PAN, Aadhaar, Form-16, bank_statement, sale_agreement, property-tax, OC, GST return, Udyam…)
  • config.py: Environment-driven model config (provider, model-name, URL, key, temperature)
  • llm_client.py: LiteLLM wrapper, multimodal base64 encoding, robust JSON repair for truncated responses
Fusion Layer — Holistic Risk Assessment
  • fusion.py
    • LLM merges: P2 verification report + P1 forensics report + cross-document + flag history
    • Produces overall risk score (0-100) + risk band (low/medium/high) + decision recommendation (approve/manual_review/decline)
    • Top flags WITH their source (pipeline-tag) + weight
  • Cross-pipeline corroboration is the core value-add:
    • P1 tamper localization on field X + P2 data mismatch on same field = strongly reinforced
    • Lone forensic pixel signal + content match → capped at manual_review
  • False-positive control rules (baked in system prompt):
    • Content VERIFIED unique-ID match → pixel anomaly is low confidence
    • Deterministic checks = hard evidence, raised sharply
    • Informational portal watermarks = normal, never flagged
    • Field-weighted: identity/money fields → high; construction → medium; cosmetic → low
  • Fallback fusion: when the LLM response can't be parsed, the verb derives the bar from content match_status alone
  • Flag-history feedback loop: past false-flag down-weight (bidirectional, planned)
Data Layer — SQLite (verichain.db)
  • applicants — demo applicants (APP001–APP005; name, scenario, expected score/decision)
  • documents — mock documents (doc_type, fields_json, fields_hash, digilocker_uri, ulpin)
  • itr_records — authoritative ITR database (record_key, PAN, name, AY, gross_total_income, total_tax_paid)
  • land_records — authoritative land-records database (state, district, taluka, village, survey_number, owner_name, area_hectare, parcel_id, encumbrance)
  • blockchain_log — immutable audit trail
    • Columns: applicant_id, doc_hash, risk_score, decision, timestamp, tx_hash, event_type
    • event_type: "system_verdict" or "underwriter_decision"
    • Append-only, never rewritten — only the verifications table is soft-deleted
  • verifications — persistent job results
    • job_id, applicant_id, submitted_at, doc_names, document_count, decision, risk_score, result_json, deleted flag
    • Survives restarts — results page reopens via GET fallback
  • load_authoritative.py — loads mock authoritative land + ITR records into DB
  • seed.py — seeds demo test cases
  • init_db.py — creates all tables
Infrastructure & Demos
  • Blockchain (audit log, not integrity oracle)
    • Mock tx_hash: SHA-256(applicant_id + doc_hash + risk_score) truncated to 40 hex chars
    • Logged alongside every system verdict + underwriter decision
    • Append-only blockchain_log table = "immutable audit trail"
    • Ganache/dev chain available; not required for prototype
  • mock_data/documents/ — test documents: genuine, tampered, vernacular (Marathi 7/12), AI-generated, cross-doc
  • LLM Client (LiteLLM): Multi-provider, env-driven (OPENAI_API_KEY, LLM_MODEL etc.)
  • Config: .env for secrets, .env.example as template

🔄 End-to-End Data Flow

User uploads PDF/JPG → POST /verify/batch → P1: Classify → T0 (sig/QR) → T1 (metadata/fonts/revision) → T2 (ELA/DCT/noise/copy-move) || P2: VLM Extract(2-pass) → Validators(IDS) → DB Fetch → Verify(she LLM) ↘ Fusion LLM → Results Dashboard → Underwriter decision → Audit Log
Killer Signal
Recovered prior PDF revision value → field-dependent Pipeline-2 anomaly → double-intent, 2-pipeline confirmation = highest-weight flag
P1 Deliberates
Tier 0 (provenance) + Tier 1 (structure) = hard; Tier 2 = advisory (unreliable on typed e-records)
P2 Hard Checks
PAN 5th-char vs name, Aadhaar Verhoeff, GSTIN checksum+state+PAN, transaction reconciliation — ALL deterministic, no LLM
Fusion
Input: P1 + P2 + cross-doc + flag-history → risk_score 0-100 (0=clean, 100=fraud) → authenticity inversion → decide
